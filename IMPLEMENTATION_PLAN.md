# Implementation Plan — JobHunter

Prioritised **work items** the `build` beat implements one at a time. One work
item = one branch = one PR. This file is regenerated by the `plan` beat; edit it
by running `./tools/spec-loop/loop.sh plan`, not by hand, once the loop is live.

Ordering follows the phases in `specs/04-technical-plan.md`: get ingest +
filtering working end-to-end first (the core value), then scoring, then
freshness/digest polish, then more sources.

## What's been built

- Nothing yet — the spec pack and the loop tooling exist; `src/` does not.

## Work items (planned)

### Phase 0 — Scaffold

1. **`project-scaffold`** — Create the Python package skeleton per
   `specs/04-technical-plan.md`: `src/jobhunter/` (empty stage modules with
   docstrings referencing their spec section), `tests/`, `pyproject.toml`
   (Python 3.11+, `httpx`, `pyyaml`, `pytest`, `ruff`; `dependencies` minimal),
   a `.gitignore` (ignoring `profile.yaml`, `.env`, `__pycache__`, run-state,
   digests), and a `jobhunter` CLI entry point that loads and validates a
   profile. Serves: `specs/04-technical-plan.md`.
   Validation: `python -m pytest tests/ -q` (a smoke test importing the package
   and validating `specs/profile.example.yaml` against the profile schema).

2. **`profile-schema`** — Implement loading + schema validation of `profile.yaml`
   (all fields in `specs/03-data-model.md` → Profile), failing loud on unknown
   keys or type errors, with sensible defaults. Enforce that
   `hard_requirements.remote_policy`, `exclude_locations`, and
   `locations_allowed` are honoured downstream. Serves: `specs/03-data-model.md`.
   Validation: `python -m pytest tests/test_profile.py -q`.

### Phase 1 — Ingest + filter (the core value)

3. **`joblisting-model`** — Implement the canonical `JobListing` type and the
   stable `id` derivation (normalised company+title+location hash) from
   `specs/03-data-model.md`. Serves: `specs/03-data-model.md`.
   Validation: `python -m pytest tests/test_model.py -q`.

4. **`adzuna-adapter`** — Implement the Adzuna source adapter
   (`search(query) -> [RawListing]` + `normalize(raw) -> JobListing`), reading
   the app id/key from env vars, with query building from
   `profile.queries` and graceful failure per `specs/02-functional-spec.md`
   Stage 1. Serves: `specs/02-functional-spec.md` (Stage 1–2).
   Validation: `python -m pytest tests/test_adzuna.py -q` (against recorded
   fixture payloads; no live network in tests).

5. **`normalize-stage`** — Implement normalization: salary/location parsing,
   HTML stripping, null-not-guessed, per `specs/02-functional-spec.md` Stage 2.
   Serves: `specs/02-functional-spec.md` (Stage 2).
   Validation: `python -m pytest tests/test_normalize.py -q`.

6. **`dedupe-stage`** — Implement dedupe by (company+title+location) / resolved
   URL, merging `sources[]`, per Stage 3. Serves: `specs/02-functional-spec.md`.
   Validation: `python -m pytest tests/test_dedupe.py -q`.

7. **`hard-filter-stage`** — Implement the hard filter with the filter tally,
   per Stage 4. Must enforce **remote-only** and **`exclude_locations`** (drop
   Sydney-based roles even when labelled remote), the seniority band, the
   salary floor with `keep_unknown_salary`, deal-breaker keywords, and freshness.
   Serves: `specs/02-functional-spec.md` (Stage 4).
   Validation: `python -m pytest tests/test_filter.py -q` (includes a case:
   a remote role tagged "Sydney" is dropped; a genuine remote role is kept).

8. **`phase1-cli-digest`** — Wire ingest→normalize→dedupe→filter into the CLI
   and emit a plain Markdown list of surviving roles + the run report tally.
   Serves: `specs/02-functional-spec.md` (Stage 7, minimal).
   Validation: `python -m pytest tests/test_pipeline.py -q` (end-to-end over
   fixture listings produces the expected filtered set).

### Phase 2 — Scoring + ranking

9. **`scoring-stage`** — Implement the transparent weighted-sum scorer with
   per-component sub-scores + reasons, deterministic, weights from the profile,
   per Stage 5. Serves: `specs/02-functional-spec.md` (Stage 5).
   Validation: `python -m pytest tests/test_score.py -q`.

10. **`rank-threshold`** — Sort best-first, recency tie-break, apply the
    display threshold (counted but hidden below it), per Stage 6. Serves:
    `specs/02-functional-spec.md` (Stage 6).
    Validation: `python -m pytest tests/test_rank.py -q`.

### Phase 3 — Freshness + digest polish

11. **`seen-state`** — Persist seen/dismissed ids + last-run; "new since last
    run"; a dismiss workflow, per Stage 7 + run-state in
    `specs/03-data-model.md`. Serves: `specs/02-functional-spec.md`.
    Validation: `python -m pytest tests/test_state.py -q` (re-run yields 0 new).

12. **`digest-html`** — Rich Markdown + HTML digest with header summary
    (sources used/failed, filter tally) and per-row reason, plus the JSON data
    file, per Stage 7. Serves: `specs/02-functional-spec.md`.
    Validation: `python -m pytest tests/test_digest.py -q`.

### Phase 4 — More sources + scheduling

13. **`ats-feed-adapter`** — Add a Greenhouse/Lever/Ashby company-feed adapter
    for a watchlist of target companies, per `specs/04-technical-plan.md`.
    Serves: `specs/04-technical-plan.md`.
    Validation: `python -m pytest tests/test_ats.py -q`.

14. **`scheduled-run`** — A "weekday morning digest" scheduled-run mode and its
    delivery mechanism (resolve open question 3 first). Serves:
    `specs/02-functional-spec.md` (Modes of operation).
    Validation: `python -m pytest tests/test_schedule.py -q`.

## Notes

- Items 4 and 13 must only use permitted APIs/feeds (see AGENTS.md hard limits).
- The seven **Open questions** in `specs/04-technical-plan.md` should be
  resolved before Phase 4; Phase 1–3 do not depend on them.
